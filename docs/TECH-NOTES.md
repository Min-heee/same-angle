# 기술 실사 노트 (조사 단계)

> PRD(`docs/PRD.md`)에서 뺀 기술 세부를 모은 문서입니다. **아직 실기기에서 한 번도 재지 않은, 조사 기반 메모**입니다. D1 실기기 스파이크(6절) 뒤에 실측값으로 갱신하고, 바뀐 곳은 문서 이력에 남깁니다. 조사와 정리는 Claude Code가 했고, 확인한 사실에는 출처를, 추론에는 [추론]을, 확인하지 못한 것에는 "미확인"을 붙였습니다. 본문의 "n절"은 따로 적지 않으면 **PRD**의 절 번호입니다.

## 2. 비교 좌표계와 지표 정의

### 2.1 뷰별 세부

| 뷰 | 수준 | 방식 |
|---|---|---|
| 정면 수평 | 1단계, 게이트 | 아래 지표 전부. 방향 세로 |
| 정면 숙임(헤어라인, 약 30°) | 1단계, 조건부 | 지표 전부. 얼굴 전체가 화면 안인 구도라 근접 헤어라인 구도(70° 숙임, IMI 요약)와는 다른 사진이다. 30°에서 랜드마크 떨림이 통과 문턱의 1/3을 넘으면 보조로 내린다. 방향은 실측 후 확정 |
| 좌·우 45° 사선 | 1단계, 조건부 | 같은 기준으로 실측 후 결정(Zheng 2025에서도 오른쪽 45° pitch만 등가성 미통과) |
| 정수리 | 1단계 보조 | 기준 겹쳐 보기, 폰 수평(DeviceOrientation, 화면이 위를 향하면 beta≈0·gamma≈0), 프레임 전체 클리핑, DeviceMotion 정지. **고개 각도는 재지 않고, 기준 대비 밝기·흐림도 비교하지 않는다.** 셔터는 수동, 상태는 "각도 미측정"(H11) |
| 측면 90°, 후두부·공여부, 수술 직후 근접 | 2단계 또는 범위 밖 | 폰 자세, 머리 실루엣의 위치·면적비, Pose 귀 랜드마크를 후보로 검토. 머리카락 마스크 면적·IoU는 모발량에 따라 바뀌므로 구도 지표로 쓰지 않는다 |

얼굴 모델 작동 범위: BlazeFace 모델 카드는 roll·pitch 45°, yaw 90° 이내, 얼굴 박스가 영상 변의 20% 이상을 전제로 둡니다. Face Mesh V2 모델 카드는 80° 넘게 돌아간 얼굴을 부적합으로 둡니다.

### 2.2 비교 좌표계

기준과 현재가 같은 눈금으로 재져야 크기·위치 비교가 의미를 가집니다. 변환 행렬의 이동값은 세로 화각 63°를 가정한 명목 cm라서, 기기·렌즈·화면비·크롭이 다르면 거리·위치 비교가 깨집니다(기술 실사, `face_geometry_from_landmarks_graph.cc`). 그래서 다음처럼 정합니다.

- **저장본 = 게이트가 판정한 바로 그 비디오 프레임의 캔버스 캡처.** 픽셀·화면비·처리 경로가 게이트와 같습니다. `ImageCapture.takePhoto()`는 Safari 18.4부터 지원되지만(WebKit 블로그, MDN BCD. caniuse는 아직 미지원 표기), D1 "실험 0"에서 같은 순간의 비디오 프레임과 takePhoto의 지표별 편향이 ε 안으로 확인될 때만 켭니다.
- **캡처 서명.** 사진마다 방향, 폭×높이, 화면비, 렌즈 라벨, zoom, 캡처 방식, `RULES_VERSION`을 남깁니다. **H6b**: 서명이 기준과 다르거나 기준이 참고 기준이면 크기·위치는 "참고값"으로 내리고 각도만 판정합니다(전체 보류가 아님).
- **정렬 기준은 게이트 경로(VIDEO)의 측정값**, 기록 판정은 저장본을 긴 변 약 1920px로 줄여 IMAGE 모드로 잰 값입니다. 두 경로의 편향은 D1에 재서 ε에 반영합니다.
- 오버레이는 검출기 입력과 같은 크롭 상자에 그립니다.

### 2.3 지표 정의 원본

| 지표 | 정의 | 통과 | 보류(H4) | 불일치 | 근거 |
|---|---|---|---|---|---|
| yaw·pitch·roll | 행렬에서 스케일을 나눈 뒤 분해한 각의 기준 대비 차 | ≤ 3° | 3~5° | > 5° | 장비 고정 촬영의 등가 마진 ±2°(Zheng 2025, 인용 근거 없는 마진), 앱 재위치 문턱 5°(Caiazza 2026), 생체인식 정면 사진 ±5°(ISO/IEC 19794-5, NIST 자료 재인용) 사이 |
| 크기 | \|ln(기준 \|tz\| ÷ 현재 \|tz\|)\| | ≤ 0.025 | 0.025~0.04 | > 0.04 | FAIN의 면적비 k=0.05(Hashimoto 2024)를 선형으로 환산(√). FAIN은 Apple Vision 기준이라 측정 방식이 다름 |
| 위치 | 얼굴 중심 차 ÷ 화면 짧은 변 | ≤ 0.03 | 0.03~0.05 | > 0.05 | FAIN도 무게중심에 ±k를 적용. 0.03은 제안값 |
| 폰 기울기 | DeviceMotion 중력의 atan2(gx, gy) 기준 대비 차 | ≤ 2° | 2~4° | > 4° | 제안값. 폰 자세는 머리 자세와 다르다 |
| 클리핑 | 피부 패치에서 휘도 ≤ 5 또는 ≥ 250 비율(절대) | ≤ 2% | 2~5% | > 5% | 제안값. 노출 사고만 거른다 |
| 밝기·흐림 | 피부 패치(뺨·콧등·눈 밑 랜드마크 다각형, 128² 재표본)의 평균 휘도 차, 라플라시안 분산 비 | 기록·경고만 | — | — | 자동노출을 끌 수 없어 거칠고, 흐림은 정지 판정이 먼저 거른다. 이마·모발은 넣지 않는다 |
| 정지 | 길이 ≥ 0.3초·프레임 ≥ 6개 창의 각도 변화폭, 중심 이동 | ≤ max(1°, 3σ) | — | 미충족이면 닫힘(H7) | σ는 한 손 촬영 실측(실험 1) |

**이 표의 숫자는 조사에 근거한 초깃값 제안이고 확정값이 아닙니다.** 모발 사진 전용 수치 허용오차는 조사에서 찾지 못했고, 근거는 대부분 얼굴 사진 분야입니다. 확정은 7절 실측 뒤 제가 합니다. 원칙은 세 가지입니다. 통과 문턱은 한 손 정지 상태 잡음의 3배 이상, 탐지 상수와 판정 경계는 값이 같아도 이름을 따로, 각도 비교는 위치·크기가 통과한 뒤에만(얼굴이 중앙을 벗어나면 행렬이 비뚤어진다는 이슈, mediapipe #4759). 위치·크기가 불통과면 각도는 "위치 먼저"로 표시합니다. 밝기 통과는 같은 조명을 뜻하지 않으므로 조명과 촬영 자리는 체크리스트로 받습니다.

### 2.4 1회차

**1회차.** 1회차는 이후 모든 비교의 기준이라 가장 엄격해야 합니다. 뷰별 프로토콜 목표값(초깃값)을 기준으로 같은 3단 판정을 합니다. 정면 |yaw|·|roll| 0±3°, 폰 기울기 0±2°, 카메라 높이 = 환자 눈높이(체크리스트, 카메라 기준 pitch는 카메라 높이에 따라 달라 프랑크푸르트 수평면과 같지 않음). 숙임 pitch 약 30±5°, 사선 |yaw| 45±5°(부호·값은 실측 후). 1회차 오버레이는 뷰 도식(윤곽·중심선)이고, 찍은 직후 "이 사진을 기준으로 쓸까요?"를 묻습니다. 기준을 나중에 다시 지정하면 기록에 남습니다.

## 3. 웹(아이폰 사파리)의 대가

- 카메라는 HTTPS에서만 열립니다. 아이폰에서 LAN의 http 개발 서버로는 열리지 않으므로 실기기 시험은 Vercel 프리뷰에서 합니다.
- **노출·초점·ISO를 고정할 수 없습니다.** WebKit `applyConstraints`는 zoom, torch, whiteBalanceMode 등만 지원하고 focusMode·exposureMode가 없습니다(`AVVideoCaptureSource.mm`). 그래서 밝기는 셔터를 막지 않습니다.
- `facingMode:'environment'`는 멀티카메라 가상 장치를 먼저 잡고, zoom 1.0에서도 렌즈가 자동 전환된다는 미해결 보고가 있습니다(iPhone 15 Pro). 근접 촬영에서 화각이 바뀔 위험은 [추론]입니다. 장치 라벨은 현지화되므로 영어 문자열로 매칭하지 않습니다.
- 비디오 프레임 해상도는 기기 포맷에 따라 다르며 실측 전입니다. "720p가 최대"라는 주장은 2019년 글이라 근거로 쓰지 않습니다.
- 사파리는 사이트와 상호작용 없이 7일간 사파리를 쓰면 스크립트 저장소를 지웁니다(홈 화면 웹앱 제외, WebKit 2020). 기기 안 보관을 기본값으로 두지 않은 이유 중 하나입니다.
- 캔버스 한 장의 픽셀 수와 전체 캔버스 메모리에 한도가 있고, GPU 위임은 예외 없이 조용히 틀릴 수 있습니다(세그멘터 #6142). D1에 CPU 결과와 대조합니다.
- **MediaPipe 사용 통계 전송.** `@mediapipe/tasks-vision` 1.0.1 은 `createFromOptions` 마다 로거를 만들고, 60초마다·`close()` 때 `https://odml.pa.googleapis.com/v1/log` 로 `POST`(`application/x-protobuf`, `x-goog-api-key` 헤더)합니다. 내용은 플랫폼(userAgent 의 iPhone 여부)·라이브러리 버전·과제 종류·실행 모드·초기화/추론 지연이고 끄는 옵션이 없습니다(`vision_bundle.mjs` 의 로거 클래스, 엔진 생성 경로가 조건 없이 로거를 만듦). 패키지 README "Privacy Notice"(2026-06-05)는 성능·사용 지표를 Google 로 보낸다고 적고, 사용자에게 알리고 동의를 받을 책임을 앱 개발자에게 둡니다. 입력 이미지·영상은 보내지 않는다고 같은 문서가 적습니다. 커스텀 헤더 때문에 사전 요청(OPTIONS)도 생깁니다. 같은각도는 이 요청을 보내지 않는 쪽을 택했습니다: 강제 CSP `connect-src 'self' https://storage.googleapis.com/mediapipe-models/`(배포본) + fetch 가드(`src/spike/netguard.ts`, 모든 환경). 로거는 fetch 예외를 잡으면 오류 상태로 바꾸고 주기 전송을 멈춥니다. 막힌 요청은 점검 페이지 11번에 출처·메서드·횟수로 남깁니다.
- Face Mesh V2 모델 카드의 전제는 전면 카메라 셀카 영상입니다. 후면 카메라로 다른 사람을 0.5~1m에서 찍는 조건은 그 밖이며, 정확도는 실측 전까지 미검증입니다.

## 4. 얼굴 변환 행렬과 합성 데이터

**왜 얼굴 변환 행렬인가.** FaceLandmarker 결과에는 world 좌표가 없고 정규화 이미지 좌표 478점과 4×4 변환 행렬만 있습니다. 정규화 좌표로 각을 재면 화면비 때문에 틀어집니다. 행렬은 정규 얼굴 모델(468점, cm)에서 현재 얼굴로 가는 회전·균등 스케일·이동이고 열 우선 16개 값입니다(`matrix.cc`, `procrustes_solver.cc`). s = ‖첫 열‖로 나눈 뒤 R = Ry·Rx·Rz로 분해합니다: pitch = asin(−R₁₂)(입력은 [−1,1]로 클램프), yaw = atan2(R₀₂, R₂₂), roll = atan2(R₁₀, R₁₁). 이 규약과 부호는 [추론]이라 `YAW_SIGN` 같은 상수 한 곳에 격리하고, 합성 생성기와 안내 문장이 같은 상수를 읽습니다. 축별 차 대신 상대 회전각 θ로 판정하는 방안은 D2에 검토합니다.

**합성 데이터.** 정규 메시는 Apache-2.0 헤더가 있는 `geometry_pipeline_metadata_landmarks.pbtxt`에서 추출해 NOTICE와 함께 넣습니다. 생성기는 순수 함수이고 시드 고정·1e-6 반올림이라 다시 만들면 바이트가 같습니다. 합성은 468점, 실제는 478점을 받고 없는 점을 채우지 않습니다. 합성 입력은 MediaPipe를 거치지 않으므로 **행렬 분해 이후 단계만 검증합니다.** 게이트는 타임스탬프를 입력으로 받고 내부에서 시계를 부르지 않습니다.

## 5. 실험 세부

- **실험 0(D1): 경로 편향.** 같은 순간의 비디오 프레임·takePhoto를 각각 VIDEO·IMAGE 경로로 재서 지표별 편향을 봅니다.
- **실험 1: 잡음 바닥.** 폰 고정과 한 손 두 조건으로 30초씩, 뷰별로 지표의 프레임 간 σ를 잽니다. 통과 문턱이 3σ보다 작으면 올리고 그 사실을 적습니다.
- **실험 2: 자유 촬영 10장 vs 게이트 촬영 10장.** 촬영자는 조력자 1명(비전문가), 피사체는 저입니다. 조력자 얼굴은 찍히지 않고 사진은 저장하지 않으며 측정 숫자만 남깁니다. 순서는 ABAB로 교차하고 한 손·거치를 기록합니다. 항목: 각도 표준편차, 크기 변동, 위치 표준편차, 장당 소요 시간, 게이트가 열릴 때까지 걸린 시간, 우회 비율, 안내를 듣고 한 번에 맞춘 비율. **사전 기준:** 게이트 쪽 yaw·pitch 표준편차가 자유 촬영의 절반 이하, 장당 중앙 소요 시간 증가 10초 이하, 20초 안에 열리는 비율 80% 이상, 우회 비율 20% 이하. 못 미치면 문턱 완화를 검토하고 그 과정을 적습니다.
- **실험 3: 반복 앉기.** 일어났다 다시 앉아 10회 이상 찍고, 기준과의 차 90퍼센타일로 경계가 달성 가능한 값인지 봅니다.
- **모델과 독립된 측정.** 게이트와 같은 모델로만 재면 순환 채점입니다. 그래서 사진 쌍마다 사람이 눈꼬리·코끝 3점을 직접 찍어 편차를 계산합니다.
- **조력자가 없을 때.** 가발을 씌운 마네킹 머리와 각도 눈금을 깐 회전판으로 부호·분해 오차를 잽니다. 마네킹 얼굴이 검출되는지는 D1에 확인합니다[추론]. 삼각대로 혼자 한 결과는 "피사체 입장만 검증"으로 따로 적습니다.
- **합성 검증과 변이.** `scripts/mutate.mjs`가 변이마다 스크래치 사본에 패치를 걸고 vitest 실패를 기대합니다. 목록: 행렬 행 우선 읽기, 스케일 미제거, asin 클램프 제거, 크기 비율 역수, 신뢰 신호 기본값 채움, 각도 차 0 고정, 기준 = 현재, 기준 누락 → 1회차 경로, 기준 지표 누락 → 0, 뷰 선언 상수 고정, 위치 선행 미연결, 캡처 서명 무시, 정지 판정 미연결, 한 프레임 통과, H10 계산만 하고 미연결, 우회 사진을 일치로 표시, 피부 패치에 모발 포함, 좌우 반전 무시. 결과표(변이·잡은 테스트·커밋 해시)는 살아남은 변이까지 README에 싣습니다. 통과한 테스트의 수는 커버리지의 증거가 아닙니다.
- **실측 픽스처.** D1에 제 머리로 자세 6개(정면, 자기 왼쪽·오른쪽 약 20°, 숙임, 젖힘, 기울임 = 오른쪽 귀를 오른쪽 어깨 쪽으로)를 후면 카메라·폰 거치로 취하고 행렬 16개 숫자만 `tests/fixtures/real-matrices.json`으로 커밋합니다(이미지·랜드마크 없음). 부호와 안내 방향 테스트는 이 실제 데이터로 합니다. 부호 오류는 합성 검증으로 잡히지 않기 때문입니다. '왼쪽'·'오른쪽 귀'는 찍히는 사람 기준이고, 방향이 없는 "기울임"으로는 roll 부호를 정할 수 없어 방향을 정의에 넣었습니다. 픽스처마다 찍은 카메라(facingMode·트랙 라벨·영상 크기)가 보고서 `sections.fixtures.data.captures` 에 함께 남습니다(전면 카메라 프레임은 좌우가 뒤집혀 있을 수 있어 yaw·roll 부호 판정에 필요).
- **제품 지표.** 카메라 없는 브라우저에서 세 상태와 비교 화면까지 30초. 실기기 네트워크 기록에서 허용 목록 밖 요청과 POST/PUT 0건. 테스트 수는 명령어·커밋 해시·날짜와 함께 적습니다. GitHub Actions는 계정 결제 문제로 돌지 않으므로, Vercel 빌드 명령을 `npm run verify`(test·typecheck·lint·build)로 두어 배포가 곧 검증 실행이 되게 하고, 돌지 않는 CI 배지는 달지 않습니다.

## 6. D1 실기기 스파이크 체크리스트

**D1 실기기 스파이크 체크리스트.** 개발 맥에 카메라가 없어 실사용 경로는 제 아이폰으로만 검증할 수 있습니다. 미루면 좌표계·부호 결함이 마감 직전에 드러납니다.

| 확인 | 통과 기준 | 실패 시 |
|---|---|---|
| CPU 추론 fps, 초기화 시간, GPU 위임 정확성 | CPU 8fps 이상, GPU 결과가 CPU와 ε 안 | 정지 창을 0.5초로 늘리고 H3 기준 조정 / GPU 끔 |
| yaw·pitch·roll 부호 | 픽스처가 [추론] 규약과 같음 | 상수 반전, 테스트 갱신 |
| takePhoto와 비디오 프레임의 화각·종횡비·편향 | ε 안 | 캡처를 비디오 프레임으로 통일(기본값) |
| 단일 광각 `deviceId` 선택, 한국어 렌즈 라벨, 근접 렌즈 전환 | 선택 가능, 전환 없음 | 라벨을 기록하고 H6b로 처리 |
| `numFaces: 2`의 비용, `visibility` 실제 값 | fps 하락 20% 이내 | `numFaces: 1`로 두고 H1의 "2명" 조항 삭제 |
| 30° 숙임·45° 사선 랜드마크 떨림, 마네킹 검출 | σ가 통과 문턱의 1/3 이하 | 해당 뷰를 보조 모드로 |
| H2가 뜻하는 촬영 거리, 회전 시 스트림 크기 변화 | 기록 | 뷰별 방향 고정 |
| 여러 파일 공유 시트·파일명 보존, `<img>` 길게 눌러 저장 | 파일 앱에 이름대로 저장 | 한 장씩 저장 + 요약 이미지 |
| DeviceMotion·DeviceOrientation 권한과 세로 상태 안정성 | 버튼 한 번으로 허락 | 폰 기울기 지표를 기록 전용으로 |
| 웹 인스펙터 네트워크 기록, CSP 동작 | 허용 목록 밖 요청 0건. `odml.pa.googleapis.com` 요청이 기록에 없음(가드가 보내기 전에 막아 점검 11번 "가드가 막은 요청"에만 잡힘), POST/PUT 0건. 11번 CSP 강제 시험이 `connect-src` enforce 위반으로 막힘(0번 위반 목록에도 enforce 로 기록) | CSP 수정. 강제 시험이 막히지 않으면 가드만 남은 것이므로 헤더 전달부터 확인 |

**초기화 시간 읽는 법.** 점검 2번 불러오기 기록의 `simdCheckMs`(`FilesetResolver.forVisionTasks`)는 SIMD 지원만 탐지하고 파일을 받지 않습니다. WASM(약 12MB) 받기·컴파일과 모델(약 3.6MB) 받기는 전부 `wasmModelInitMs`(`createFromOptions`)에 들어갑니다(`vision_bundle.mjs`). 그래서 첫 로드(통신 포함)와 두 번째 로드(캐시)를 나눠 적고, 이 단계의 제한 시간은 60초로 둡니다.

**그 밖의 미확인.** IMAGE 모드의 EXIF 회전 반영(안전한 경로는 `createImageBitmap`), FaceLandmarker와 캔버스의 메모리 합, 아이폰에서 `getImageData`와 지표 계산 비용, takePhoto의 플래시 동작(`fillLightMode`), 홈 화면 웹앱과 사파리 탭의 저장소 분리와 standalone 모드의 카메라 권한 재요청(WebKit 버그 181849·215884, F12를 켤 때만 해당), 얼굴이 중앙을 벗어났을 때의 각도 편향 크기, 음영 합성 머리가 픽셀 지표 시연에 충분한지(부족하면 시연은 픽셀 지표를 보여 주지 않는다고 표시).

## 7. 규제 조사 메모

**규제.** 기준 사진을 저장·조회하는 기능은 식약처 1등급 "의료영상전송장치소프트웨어" 정의와 글자가 겹칠 수 있고, 영상에서 촬영 조건을 계산하는 기능이 2등급의 "분석"으로 읽힐지도 미확인입니다(2020 행정예고안, 현행 품목 분류 미확인). 의료기기로 판단되면 AI 기본법의 고영향 해당 여부도 다시 봐야 합니다. 의료기관 도입 전에는 해당 여부를 확인해야 하고, 이 데모는 그 확인을 대신하지 않습니다. 이 검토는 AI가 조사한 것이고 법률 자문이 아닙니다.

이 절은 AI가 조사한 메모이고 법률 자문이 아닙니다. 실운영 전 확인할 것: 현행 식약처 품목 분류, 스마트폰 임상 사진이 "의료영상"에 해당하는지, 촬영 조건 계산이 2등급 "분석"으로 해석되는지, AI 기본법 고영향 해당 여부.

## 10. D1 점검 페이지 사용법

개발자(저)가 아이폰에서 혼자 따라 하는 순서입니다. 점검 페이지(`/spike/`)는 제품 화면이 아니라 6절 체크리스트를 재는 도구이고, 각 섹션 제목 아래에 해당 항목 번호가 있습니다.

### 10.1 여는 법(HTTPS 로 배포한 뒤)

1. 아직 배포하지 않았습니다. 배포는 Vercel 에 이 저장소를 연결해서 합니다(빌드 명령은 `vercel.json` 의 `npm run verify`, 테스트·타입·린트·빌드가 모두 통과해야 배포됨). 배포가 끝나면 프리뷰 또는 프로덕션 주소가 생깁니다.
2. 아이폰 **사파리 탭**에서 배포한 주소 뒤에 `/spike/` 를 붙여 엽니다. 카메라는 HTTPS 에서만 열리므로 맥의 `npm run dev`(LAN http)로는 안 됩니다. 홈 화면 웹앱이 아니라 사파리 탭으로 엽니다(저장소·권한이 따로 놀 수 있음, 6절 '그 밖의 미확인').
3. 시작 전 설정: 설정 > 디스플레이 및 밝기 > **자동 잠금 = 안 함**(흔들림 30초 기록이 최소 자동 잠금 30초와 겹치고, 화면이 꺼지면 그 기록은 버려짐). **저전력 모드 끔**(켜면 자동 잠금이 30초로 강제됨). **무음 모드 해제·볼륨 올림**(삐 소리가 후면 카메라 촬영 중 유일한 신호. 사파리 16.4+ 는 페이지가 무음 스위치를 우회하려 시도). 와이파이 연결(첫 로드에 WASM 약 12MB·모델 약 3.6MB).
4. 네트워크 기록(6절 항목 10)을 함께 남기려면 설정 > Safari > 고급 > 웹 속성 검사기를 켜고 아이폰을 맥에 연결해, 맥 사파리 개발 메뉴에서 이 탭의 네트워크 기록을 **페이지를 열기 전부터** 켭니다.

### 10.4 CSP 를 일부만 강제하고 나머지를 Report-Only 로 둔 이유와 강제로 바꿀 조건

지금 `vercel.json` 은 두 헤더를 붙입니다. 강제(`Content-Security-Policy`)는 `connect-src`(자기 출처 + 모델 버킷 경로)·`form-action`·`base-uri`·`frame-ancestors` 뿐이고, 나머지(`default-src`·`script-src 'unsafe-inline' 'wasm-unsafe-eval'`·`worker-src`·`media-src`·`img-src`·`style-src`)는 Report-Only 로 관찰만 합니다.

- **connect-src 를 먼저 강제한 이유:** MediaPipe 1.0.1 의 사용 통계 전송(3절)이 실제로 나가는 요청이라 관찰만으로는 약속(F10)을 지킬 수 없습니다. `connect-src` 는 WASM 실행·GPU 위임·카메라 스트림·공유 시트를 막지 않습니다(코드 검토 때 맥 크로미움에서 이 헤더 아래 CPU·GPU 모델 불러오기가 성공했다. 아이폰 사파리는 미확인).
- **나머지를 관찰로 둔 이유:** 아이폰 사파리에서 MediaPipe WASM(`wasm-unsafe-eval`), GPU 위임(워커·blob), 카메라 스트림(`mediastream:`), 공유 시트, Next 정적 내보내기의 인라인 스크립트가 이 정책 아래에서 무엇을 요구하는지 한 번도 재지 않았습니다. 처음부터 강제하면 점검 자체가 막혀 무엇이 모자랐는지 알 수 없습니다. Report-Only 에서도 사파리는 위반마다 `securitypolicyviolation` 을 내므로 0번이 모읍니다.
- **D1 뒤 강제로 바꿀 조건(모두 충족):**
  1. 아이폰 D1 보고서 `sections.env.data.cspViolations` 에 disposition `report` 위반이 0건이다. 0~12번 전 섹션(CPU·GPU 불러오기, 추론, 같은 프레임 비교, takePhoto, 옛 사진, 공유)을 돌린 뒤의 보고서여야 한다.
  2. 11번 CSP 강제 시험이 `connect-src` enforce 위반으로 막혔다(사파리가 강제 헤더를 실제로 지킴).
  3. 웹 인스펙터 네트워크 기록에서 허용 목록 밖 요청·`odml.pa.googleapis.com` 요청·POST/PUT 이 0건이다.
  4. 위반이 있었다면 정책을 고친 커밋 뒤, 위반이 났던 섹션만 다시 돌려 0건을 확인했다.

  충족하면 Report-Only 의 지시어를 강제 헤더로 옮기고, `src/csp.test.ts`·README·이 절을 같은 커밋에서 고칩니다. 그 뒤에 새로 더하는 지시어는 한 번의 실기기 점검 동안 Report-Only 로 먼저 둡니다. `script-src 'unsafe-inline'` 은 정적 내보내기의 인라인 스크립트(하이드레이션 데이터, CSP 위반 수집기)에 필요하다고 보고[추론] 강제 전환 때도 남기되, 없앨 수 있는지(해시)는 따로 봅니다.
